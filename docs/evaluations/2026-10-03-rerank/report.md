- 每題只規劃、搜尋一次並保存候選池，重排前後比較同一份資料；Jev 每題重跑三次。不同組候選池可能不同，不能將跨組差異全歸因於程式版本。
- 重排前固定取原排序前五部；PR 重排後上限五部、門檻 0.5。**目前正式流程回傳上限為十部**，此處只評前五名，未把十部縮成五部的產品影響當成排序收益。
- 在查看每組 Jev 分數前，由本次助理依原始需求、候選簡介／類型與已確認篩選條件標註 0／1／2：無充分符合證據、部分符合、明確符合。每個候選都有理由；這是助理的 metadata 判讀，**不是使用者或獨立人工盲評**。
- 缺少簡介者保守標為 0，代表不能證明符合，不代表作品實際不相關。這會影響指標，尤其是 Jev 可能憑片名與既有知識評高分的作品。
- Precision@5 只把 2 分算命中，分母固定五；不足五部的空位算未命中。nDCG@5 用 `(2^grade−1)/log2(rank+1)`，理想排序取同池標註前五名，不能反映池外漏掉的好電影。
- nDCG 可能因去除低分片而升高，但結果變短不一定改善使用體驗，因此另外保留結果數、誤刪與不穩定案例。

## 收益、成本與等待時間

- 9 題有效候選的平均 Precision@5：**33.3% → 53.3%，增加 20.0 個百分點**。nDCG@5：0.566 → 0.919。若失敗題的 Precision@5 前後都算零，十題平均為 30.0% → 48.0%。這些是小樣本、助理標註的相關性代理指標，不能當作已證明使用者滿意度提升。
- nDCG 判讀為 7 題改善、1 題退步、1 題相同、1 題上游失敗；Precision@5 則為 5 題改善、1 題退步、3 題相同、1 題上游失敗。
- 每次 Jev 平均 **US$0.00039661**，依本次有效案例組成，一萬次推薦多約 **US$3.97**。20 候選的六題每次約 US$0.00050～0.00063；額外費用約 US$5.03～6.28／一萬次。
- 目前主分支成功九題的規劃平均估算 US$0.00020283；加上 Jev 平均為 US$0.00059944，即 **約 2.96 倍（增加 195.5%）**。絕對金額低，但它沒有省掉原本的規劃呼叫。
- 規劃費用以實際 token usage 和 [GPT-6 Luna 官方價格](https://developers.openai.com/api/docs/models/gpt-6-luna)估算：每百萬 input US$0.10、cached input US$0.01、output US$0.50；不是帳單實扣。Jev 使用每次 API 回報的費用，未用估計 token 替代。[OpenRouter 模型價格](https://openrouter.ai/typesafe/jev-1.13/api)目前列 input US$0.042／百萬、output US$0。
- 兩組所有 Jev 實測合計 **636 個外部請求，US$0.01750972**；此數字僅含 Jev，不含 20 次原始規劃與一次診斷規劃。原始上游失敗題未保存 token usage，不能宣稱已完整核算整次實驗費用。
- Jev 額外等待：p50 **332 ms**，p95 **1462 ms**，平均 **542 ms**，最大 **1889 ms**。p95 使用 nearest-rank，27 次樣本不足以估正式環境尾端延遲。
- 目前主分支 baseline 平均 2964 ms；配對加上 Jev 後平均 3506 ms，增加約 18.3%。
- `pairedBackendMs` 是同池「一次 baseline 實測＋該次 Jev 實測」的相加值，**不是 27 次完整端到端請求**。baseline 包含本機規劃與 TMDB，planMs 包含傳輸／讀取，tmdbMs 為剩餘階段的近似值。未測遠端 Edge Function 啟動、Auth／配額、歷史紀錄、瀏覽器網路與 React 呈現，不能把它叫作前端點擊到畫面完成時間。
- 所有 636 次 Jev 回應均有費用、有效分數且無失敗；有候選的案例沒有全部失敗備援，也沒有被全部過濾成空清單。PR 原版零候選那題雖標記 fullFallback，實際未呼叫 Jev，不能算 provider 故障。

## 決定是否採用的關鍵問題

1. **明確條件可能被錯殺。** 第 6 題四部候選都已通過年份、科幻與 Amy Adams 篩選，《雲端情人》卻在兩組共六次都被移除。額外查詢 TMDB `/movie/152601/credits` 確認 Amy Adams 飾演 Amy，證據保存在 diagnostics.json。PR 傳給 Jev 的 candidate state 沒有演職員資料、resolvedPeople，也沒有 popularity／vote_count；只靠 summary、labels 與簡介重新推斷「有 Amy Adams、受歡迎」，會把查詢已確認的條件當成未知。先前單筆冒煙測試把這次移除當成正向篩選，這次證據顯示該解讀不成立。
2. **Jev 救不了搜尋失敗或窄候選池。** 第 9 題在兩組都失敗；額外診斷發現 planner 將 `career failure` 標成 explicit TMDB keyword，搜尋無法解析就中止。第 10 題把 `human connection` 當 explicit keyword，只得到《The Hole》，Jev 三次不改結果但仍收費。規劃 prompt 雖已要求抽象主題放 qualities，模型仍可能違反。
3. **門檻 0.5 有可見波動。** 第 4 題《開箱靈魂》有時過門檻、有時不過；第 7 題會帶回絕症電影，甚至含霸凌／自殺的《聲之形》，仍不完全符合平靜療癒。Jev 分數不是硬限制驗證，也不是觀眾喜好概率。
4. **資料缺漏會降低可解釋性。** 《Dilbert》沒有提供簡介卻反覆得到高分進前五；《Socias por accidente》也在無簡介下進榜。不能證明它們不合適，但與 PR criteria 要求 supplied metadata evidence 有落差。
5. **結果縮短可能傷害選擇。** 浪漫喜劇題 20 部評完僅留一部，燒腦題剩一到兩部；這能去除不符的作品，但尚未證明一部結果比多部可選更符合產品需求。現有上限十部，PR 上限五部，整合時要明確保留產品要求。
6. **增加外部請求與尾端等待。** 一題 20 候選就多 20 個外部請求；Promise.allSettled 雖並行，仍等待最慢一個。短期費用低，主要代價是可靠性、限流與使用者等待。

## 建議採用方式

先保留目前規劃／搜尋模組，只接 PR 的最小 rerank 能力。當請求有需要判讀的 qualities／觀看體驗，且有多部可選時使用 Jev；只有已確認的演員、年份、語言等條件，或只有一部候選時，不需要付出這次額外呼叫。這個條件式方案尚未實作，也未直接量測其節省，不能把它寫成已達成收益。
送入模型的語意評分目標應只包含尚未由搜尋驗證的偏好，避免重判已確認的人物與數值條件；缺少簡介要有一致的處理規則；門檻附近要減少不必要刪除。先修第 6 題誤刪及第 9 題抽象 keyword 阻斷，再用本次固定池驗證回歸。必要時針對候選不足改善召回，而不是期待 rerank 產生新電影。
完成這些最小調整後，再請使用者盲比結果並實測瀏覽器提交到完成的時間；目前資料足以支持「值得做一個限縮版本」，不足以支持「PR 原樣直接上線」。
